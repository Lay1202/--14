# 과제 14: 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교

과제 13의 병합 정렬·퀵 정렬(First / Random / Median-of-Three 피벗)에 힙 정렬을 추가해 비교 횟수, 실행시간, 메모리 사용량을 측정했습니다. 전체 실행 로그는 `heap_merge_quick_result.txt`에 있습니다.

- 빌드: `gcc -O2 -o heap_merge_quick heap_merge_quick.c` (Visual Studio에서는 Release / x64 권장)
- 데이터: 과제 12, 13과 같은 생성기·시드·생성 순서를 써서 같은 데이터입니다(0~1,000,000 무작위 정수, 중복 허용). 그래서 병합·퀵 정렬의 비교 횟수가 과제 13과 정확히 같습니다. 각 크기에서 모든 알고리즘은 같은 원본의 복사본으로 실행합니다.
- 검증: 모든 정렬 결과의 오름차순 여부와 원본과의 합·제곱합 일치를 확인했고 전부 통과했습니다.

## 1. 측정 방법

**힙 정렬 구현:** 입력 배열 자체를 최대 힙으로 사용합니다(별도 힙 배열 없음). 마지막 부모 노드(n/2−1)부터 0번까지 `sift_down`으로 힙을 만들고(bottom-up 힙 구성), 루트를 마지막 원소와 교환한 뒤 힙 크기를 줄이면서 `sift_down`으로 힙 속성을 복구하는 과정을 반복합니다. `sift_down`은 반복문으로 구현했습니다(재귀 없음).

**비교 횟수:** 힙 구성과 복구 과정에서 값 비교를 모두 셉니다. `sift_down`에서 두 자식 중 큰 쪽을 고르는 비교 1회, 그 자식과 부모를 비교하는 1회입니다(자식이 하나뿐이면 1회). 병합 정렬은 병합 과정의 비교, 퀵 정렬은 분할 비교와 Median-of-Three의 중앙값 결정 비교를 셉니다. 루프 조건 검사는 세지 않습니다.

**실행시간:** 정렬 시작부터 끝까지만 `QueryPerformanceCounter`(Windows) / `clock_gettime`(Linux)로 재고, 배열 복사·데이터 생성·출력은 제외했습니다. 같은 원본으로 300번(워밍업 5번 제외) 반복한 평균이고 단위는 모든 알고리즘에 ms입니다. 병합 정렬의 임시 배열 `malloc/free`는 알고리즘의 일부라 시간에 포함됩니다. 병합·퀵 정렬에는 메모리 계산용 재귀 깊이 카운터가 있어 힙 정렬보다 아주 조금 불리하지만 영향은 작습니다.

**메모리 사용량(추가 메모리):** 직접 계산하는 방식입니다. 원본 배열은 제외합니다.

| 알고리즘 | 계산 방법 |
|---|---|
| 힙 정렬 | 재귀와 추가 배열이 없으므로 보조 변수를 포함한 함수 프레임 크기만 계산합니다. `heap_sort` 프레임 32바이트 + `sift_down` 프레임 48바이트 = **80바이트(n과 무관한 상수)** |
| 병합 정렬 | 임시 배열 `4n`바이트 + 최대 재귀 깊이 × 프레임 48바이트 |
| 퀵 정렬 | 추가 배열 없음, 최대 재귀 깊이 × 프레임 48바이트 |

프레임 크기는 매개변수 + 지역변수 + 반환 주소·이전 프레임 포인터(포인터 크기의 2배)를 더해 16바이트 단위로 올림한 값(64비트 빌드 기준)이며, 프로그램이 `sizeof`로 계산해 첫 줄에 출력합니다. 최대 재귀 깊이는 실행 중 기록한 값입니다. 병합·퀵의 `partition`, `merge_arrays` 같은 보조 함수 프레임(수십 바이트)은 제외했고, 힙 정렬은 이런 함수들이 유일한 추가 메모리라서 포함했습니다. 실제 프레임 크기는 컴파일러 최적화에 따라 다를 수 있으므로 측정이 아닌 계산한 추정값입니다.

## 3. 분석

### 비교 횟수
- **힙 정렬이 가장 많고, 병합 정렬이 가장 적습니다.** n=20,000(100개 평균)에서 힙 약 51.1만 회, 퀵 31.9만~34.0만 회, 병합 약 26.1만 회입니다. 힙은 병합의 약 1.96배, 퀵(First)의 약 1.5배이고, 이 순서는 모든 크기에서 같습니다.
- **원인(힙 정렬):** 힙 정렬은 추출 단계에서 루트에 올라간 원소(원래 마지막 원소라 대개 작은 값)를 바닥까지 내려보내야 합니다. 한 단계마다 "두 자식 중 큰 쪽 고르기"와 "부모와 비교"로 비교가 2번 들기 때문에 원소 하나당 약 2 log₂n번이 필요합니다. 전체로는 약 2n log₂n − 3n회이고(n=20,000에서 이론값 약 511,500, 측정 평균 510,740), 병합 정렬의 n log₂n − 1.25n보다 약 2배 많습니다. 힙 구성 단계(약 2n회)는 전체에서 차지하는 비중이 작습니다.
- **병합·퀵:** 병합은 항상 정확히 반으로 나눠 약 n log₂n − 1.25n회이고, 퀵은 분할이 완벽하지 않아 평균 약 1.39 n log₂n회입니다(과제 13과 동일).
- **크기 증가:** 세 알고리즘 모두 n이 2배가 되면 비교 횟수가 2배보다 조금 더 늘어납니다(n log n 증가). 힙은 n=1,000의 16,855회에서 n=16,000의 397,491회로 약 23.6배(n은 16배)입니다.

### 실행시간
- **퀵 정렬이 가장 빠르고, 힙 정렬과 병합 정렬은 비슷합니다.** n=20,000에서 퀵(First) 1.31ms, 퀵(Median3) 1.40ms, 퀵(Random) 1.47ms, 힙 1.83ms, 병합 1.86ms입니다. 퀵(First)보다 힙·병합이 약 40% 느리며, 이 순서(퀵 < 힙 ≈ 병합)는 모든 크기에서 유지됐습니다. 힙과 병합 사이의 우열은 크기마다 뒤바뀔 만큼 작은 차이(약 3% 안팎)입니다.
- **원인:** 비교 횟수만 보면 병합이 힙의 절반인데도 시간이 비슷한 이유는 데이터 이동 비용 때문입니다. 병합은 모든 단계에서 임시 배열로 복사했다가 되돌려 쓰는 작업(약 2 n log n번의 쓰기)과 임시 배열의 할당/해제가 필요합니다. 힙은 비교는 2배 많지만 제자리에서 교환만 하며 쓰기가 적습니다. 두 효과가 비슷해서 시간이 비슷해졌습니다. 퀵 정렬은 제자리에서 배열을 순차적으로 훑으며 분할하고 비교도 병합보다 약간 많은 정도라 가장 빠릅니다. 힙 정렬은 부모와 자식 사이를 건너뛰어 접근하기 때문에 순차 접근보다 캐시 효율이 떨어질 수 있습니다(이번 크기에서는 데이터가 작아 영향이 크지 않았습니다).
- **크기 증가:** 세 알고리즘 모두 n이 커질수록 시간이 n log n 이상으로 늘어납니다. n=1,000에서 20,000(20배)로 갈 때 시간은 힙 약 59배, 병합 약 55배, 퀵(First) 약 77배로, n log n 예측(약 29배)보다 더 크게 늘었습니다. 데이터가 캐시 크기를 넘어서는 영향일 가능성이 있지만 이번 실험만으로 확정할 수는 없습니다.

### 메모리 사용량
- **힙 정렬은 크기와 상관없이 80바이트**로 가장 적습니다. 입력 배열 자체를 힙으로 쓰고 재귀가 없어서 보조 변수만 필요하기 때문입니다(O(1)).
- **퀵 정렬은 약 0.8~1.8KB**로 재귀 스택만 필요합니다. 크기가 16배(1,000→16,000)가 되어도 816~1,008바이트에서 1,248~1,680바이트로 조금만 늘어납니다(재귀 깊이가 log n에 비례). 분할이 균형 잡힐수록 깊이가 얕아서 Median3(평균 약 26단계)가 First·Random(약 33~34단계)보다 적었습니다.
- **병합 정렬은 n=20,000에서 80,768바이트**로 퀵의 약 45~65배, 힙의 약 1,000배입니다. n에 비례하는 임시 배열(4n바이트)이 대부분이라 n이 2배가 되면 메모리도 약 2배가 됩니다(O(n)).

### 퀵 정렬의 피벗 선택에 따른 차이
- 100개 평균 비교 횟수는 Median3(319,084)이 가장 적고 First(338,593)와 Random(340,238)은 거의 같습니다. 세 값의 중앙값은 극단값이 될 확률이 낮아 분할이 더 균형 잡히기 때문입니다. 단일 실험에서는 운에 따라 순위가 바뀌었습니다(n=8,000은 Random이 최소, n=20,000은 Random이 최대).
- 균형 잡힌 분할 덕분에 재귀 깊이도 줄어 Median3의 스택 사용량이 가장 적었습니다.
- 실행시간은 비교 횟수가 가장 적은 Median3이 아니라 First가 가장 짧았습니다(n=20,000에서 1.31 vs 1.40ms). 중앙값을 구하는 추가 비교·분기와 Random의 난수 생성 비용이 분할 개선 이득을 상쇄했습니다. 다만 이 차이는 5~10% 수준이라 환경에 따라 바뀔 수 있습니다. 무작위 데이터에서는 First도 문제없지만, 정렬된 입력에서 O(n²)이 된다는 점은 과제 12에서 확인했습니다.

### 시간·공간 복잡도 비교

| 항목 | 힙 정렬 | 병합 정렬 | 퀵 정렬 |
|---|---|---|---|
| 시간(최선) | O(n log n) | O(n log n) | O(n log n) |
| 시간(평균) | O(n log n) | O(n log n) | O(n log n) |
| 시간(최악) | O(n log n) | O(n log n) | O(n²) |
| 공간 | O(1) (제자리) | O(n) 임시 배열 + O(log n) 스택 | O(log n) 스택(최악 O(n)) |
| 안정성 | 불안정 | 안정 | 불안정 |

실험 결과는 이 표와 일치합니다. 힙 정렬은 입력과 상관없이 O(n log n)이 보장되고 추가 메모리가 거의 없지만, 비교 횟수가 가장 많고 실제 속도도 퀵 정렬보다 느렸습니다. 병합 정렬은 비교 횟수가 가장 적고 최악도 O(n log n)이지만 n에 비례하는 메모리가 필요했습니다. 퀵 정렬은 평균적으로 가장 빠르고 메모리도 적지만, 피벗 선택이 나쁘면 최악 O(n²)이 될 수 있습니다.

### 결론
비교 횟수는 병합 < 퀵 < 힙 순, 실행시간은 퀵 < 힙 ≈ 병합 순, 메모리는 힙 < 퀵 < 병합 순이었습니다. 하나의 알고리즘이 모든 면에서 우세하지는 않습니다. 평균 속도가 중요하면 Median-of-Three 퀵 정렬, 최악의 경우도 O(n log n)으로 보장하면서 추가 메모리를 거의 쓰지 않으려면 힙 정렬, 안정 정렬이나 비교 횟수 최소화가 필요하면 병합 정렬이 적합합니다.
